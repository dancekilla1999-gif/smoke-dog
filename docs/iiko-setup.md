# iiko: подготовка подключения QR-меню

## Текущий статус

Заказ за столом включается только вместе: ключи, организация, группа терминалов, привязки столов, карта блюд `IIKO_PRODUCT_BINDINGS_JSON` (`menuItemId` из QR-меню и `productId` кассы) и `IIKO_ORDERING_ENABLED=1`. Цена из браузера не отправляется. Пока чего-то из этого нет, гость видит «покажите выбор официанту».

- `GET /api/qr-menu/config?table=<opaque-token>` возвращает `orderingAvailable:true` только для известного стола и полного набора настроек. Наружу уходит лишь `{label}`.
- `POST /api/qr-menu/orders` без этого набора отвечает 503 и не вызывает iiko. С набором создаёт заказ стола и ждёт `commands/status`.
- Цена и идентификатор блюда кассы берутся на сервере. Браузер присылает только id позиции меню и количество.

## Секреты

Настроить в серверном окружении Vercel, без префикса `NEXT_PUBLIC_`. Ключи не передавать в чат, не коммитить, не хранить в JSON проекта.

| Переменная | Назначение |
| --- | --- |
| `IIKO_APP_ID` | Приложение на портале разработчика iiko |
| `IIKO_CLIENT_SECRET` | Секрет приложения |
| `IIKO_API_KEY` | Ключ ресторана из iikoWeb |
| `IIKO_ORGANIZATION_ID` | Подтверждённый UUID организации Smoke Dog |
| `IIKO_TERMINAL_GROUP_ID` | Подтверждённый UUID группы терминалов |
| `IIKO_EXTERNAL_MENU_ID` | Числовой ID опубликованного внешнего меню |
| `IIKO_TABLE_BINDINGS_JSON` | Массив проверенных привязок столов |
| `IIKO_PRODUCT_BINDINGS_JSON` | Массив `{menuItemId, productId}` для позиций QR-меню |
| `IIKO_ORDERING_ENABLED` | `1` включает отправку. Любое другое значение оставляет показ официанту |

Привязка столов — массив объектов `{tokenHash,label,tableId}`. `tokenHash` — SHA-256 от случайного токена QR, hex нижнего регистра; `label` — название стола; `tableId` — UUID настоящего стола iiko. Не использовать номер стола как токен. Токены должны быть случайными, не менее 32 символов URL-safe. Массив с ошибочной или повторяющейся записью целиком отвергается. Реальных столов в коде нет; QR для столов ещё не выпущены.

## Проверка подключения администратором

Используется существующая сессия `/api/admin/login`. Для этих методов дополнительно обязательны заданные `ADMIN_PASSWORD` и `ADMIN_SESSION_SECRET`; известный секрет разработки запрещён. Все запросы — POST с заголовком `Origin` текущего сайта. Ответы не кешируются.

1. `POST /api/admin/iiko/diagnostics` — получение токена v2 и списка организаций. Возвращает `connected:true` только после успешного чтения; это **не** означает готовность заказов.
2. `POST /api/admin/iiko/catalog`, JSON `{"resource":"terminals"}` — группы терминалов организации.
3. После установки группы: `{"resource":"tables"}` — залы и столы.
4. `{"resource":"menus"}` — список внешних меню; после выбора `IIKO_EXTERNAL_MENU_ID`: `{"resource":"menu"}` — необработанная витрина для сверки.
5. `{"resource":"stopLists"}` — остатки/стоп-лист выбранной группы, с размерами.

Данные доступны только администратору. Адаптер использует фиксированный `https://api-ru.iiko.services`, список разрешённых методов чтения, таймаут и запрещает HTTP redirects. Токен живёт только внутри серверного запроса. Тела ошибок iiko не передаются клиенту и не логируются.

## Что обязательно закончить до включения заказов

1. Проверить реальный кабинет, тариф/доступ API, организацию, терминалы и столы.
2. Сопоставить каждую заказываемую позицию меню с настоящими product/size/modifier ID. Совпадение названия не является подтверждением. Весовые блюда, разные объёмы и обязательные модификаторы требуют отдельных правил.
3. Получать цену и доступность с сервера iiko; не доверять цене, составу или tableId из браузера.
4. Выпустить отдельные случайные QR-токены для подтверждённых столов. Проверять связь стола с организацией и группой терминалов.
5. Реализовать явное подтверждение заказа гостем, устойчивую идемпотентность и сверку асинхронного `correlationId` через `/api/1/commands/status`. Повтор после таймаута не должен создавать новый заказ. Не использовать память процесса Vercel как журнал заказов.
6. Не добавлять позиции в чужой открытый заказ стола только на основании номера стола. Для общего заказа нужна подтверждённая сессия/правило кассы.
7. Провести согласованную проверку на тестовом стенде iiko и только затем включать запись. Удаление заказов через API недоступно: тест на рабочей кассе может попасть на кухню и в отчёты.
